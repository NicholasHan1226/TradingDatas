# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

## TradingDatas public visual contract

- The confirmed home direction is a warm editorial canvas with an abstract generative data-material field: dispersed blue/aqua particles become ordered traces, with one restrained receipt-yellow verification accent.
- Keep `TradingDatas` as one word and retain the supplied four-square mark. Do not recreate it with CSS or inline SVG.
- The registered public domain is `tradingdatas.com`. Registration alone does not prove DNS, HTTPS, deployment, or `api.tradingdatas.com` runtime availability; verify those separately before release claims.
- Use the art system at three densities: quiet dispersal for hero/transition space, directed weave for catalog organization, and ordered lattice for receipt/provenance surfaces.
- The artwork supports product content; it must not become a chart, flowchart, trading terminal, particle globe, purple gradient, neon crypto treatment, or perpetual motion effect.
- Public pages support `zh-CN` and `en`, default from system language, plus light/dark/system appearance. Agent/MCP setup belongs under the Account experience.
- Research is a curated external-literature library organized with TradingDatas' own taxonomy. Preserve authorship and source attribution; do not present external conclusions as TradingDatas research. Language and appearance controls live inside Account, not as a separate header control.
- Research must lower the visual and reading cost of heavy papers without flattening their substance. Lead from a user question, package each paper as a recognisable reading product with source identity, orientation time, and related materials, and connect papers into curated reading paths. Keep the full taxonomy progressively disclosed rather than making the first screen a filter-heavy paper list.
- Research-path imagery may carry the persistent path title as part of the raster cover, like an editorial research product. Verify those covers in both light and dark themes; background changes must not wash out the artwork, title, borders, or adjacent metadata.
- Research covers use theme-matched companion artwork rather than a brightness filter: warm ivory/mist-blue covers on the light canvas and the existing deep navy/cyan covers in dark mode. Keep the same title, composition family, and product identity across the pair so switching appearance changes contrast, not meaning.
- The persistent top navigation is one lightweight floating rounded surface containing `Data / Research / Pricing`, one global search field, Bookmarks, and the Account icon. Follow the Hovvi-like single-layer hierarchy: the three primary destinations sit directly on the header surface as quiet text links, and current location is expressed with a fine underline rather than a nested segmented pill, filled tab, or second bordered capsule. On desktop, brand and destinations form a compact left group, search uses a bounded responsive width, and a flexible spacer separates discovery from the right-side personal actions; do not distribute every gap equally or let search consume all remaining space. Homepage and inner-page headers share one desktop top-edge offset. Global search spans datasets, external research, preparation methods, and documentation. Do not duplicate search boxes inside Data, Research, the expanded research library, or Documentation; their local controls are taxonomy/status filters rather than separate keyword search. On mobile, global search moves into the expanded floating navigation. Keep Features, Recipe, and Docs routes directly addressable for compatibility, but do not restore them as equal-weight top-navigation items.
- Global search groups results by Data, Research, Methods, and Docs; supports Arrow Up/Down, Home/End, Enter, Escape, and `Command/Ctrl + K`; announces the complete result count; and keeps at most five recent query strings in this browser only with both per-item removal and an explicit clear-all action. Each group initially exposes four results and expands in place through `Show all`; it must not route users to a duplicate page-level keyword search. Search discovery includes both authored languages, stable identifiers, category/market/cadence metadata, common Chinese/English aliases, and bounded pinyin aliases. Exact labels and dataset IDs outrank descriptions; an explicit Research/Methods/Docs intent may bring that group forward, while equal-score products preserve catalog order. Typo tolerance is limited to one insertion, deletion, substitution, or adjacent transposition in Latin tokens of at least four characters; short codes and Chinese text never receive fuzzy matching. A no-result state may offer three authored example queries but must not silently broaden the query. Only non-obvious `ID`, alias, and approximate matches receive a compact explanation beside the title; direct title/description matches stay unlabelled. Recent queries are client-side convenience state, never account sync, analytics, or runtime authority.
- Section-level navigation is quieter than the global floating surface: use an unboxed horizontal text index with compact spacing and a fine current-location underline. Do not nest another bordered pill, translucent capsule, filled active tab, or soft shadow beneath the global header. It must feel like an editorial table of contents, not a SaaS toolbar.
- Cookbook/Recipes is progressively disclosed inside Research as the preparation-method layer. It teaches query, alignment, joins, validation, and reproducibility without publishing a research conclusion; existing `/recipes/:id` detail routes remain valid deep links.
- Documentation lives under `Account -> Connect & learn` and retains deep `/docs/:slug` routes for shareable full guides. Language, appearance, Agent/MCP, subscription, usage, keys, billing, security, and saved materials also live in Account.
- Bookmarks cover datasets, external research, preparation methods, and documentation. Until an authenticated persistence contract exists, the prototype must label bookmarks as browser-local and must not imply account, cross-device, or server sync.
- On Data surfaces, never present a category as if it were a purchasable dataset. The hierarchy is `category -> individually packaged data product -> product detail`: for example, `Alternative data -> Pizza Index`. Market, company/fundamentals, event, and future categories follow the same rule. Category controls organize discovery; every listed product has its own identity, mark, contents, coverage/stability evidence, sample, and addressable detail page.
- Data-product marks use the supplied softly blended, filled abstract mini-cover language. Every category owns one stable color family and one base geometric grammar. Products inside that category inherit both, then vary the arrangement through direction, module order, density, crop, offset, mirroring, local scale, or restrained two-layer echo so they read as distinct members of one family. Support at least eight repeatable variants before reusing an arrangement. Status colors never recolor the product identity. Do not replace the marks with outline line art, generic finance glyphs, emoji, or CSS-drawn approximations.
- Keep the Data landing page progressive: the default state is a lightweight nine-category directory with representative products; selecting a category, status, or search term reveals the focused product list; full samples and detailed evidence belong on the product detail page. Products without collection history show a concise empty-evidence state instead of repeated empty charts or pseudo-metrics. Only products with actual bounded observations may expand collection-stability trends.
- Treat `Observed / Planned / Pending release` as product-stage information, not title decoration or a substitute for receipt evidence. On focused lists and detail pages, place the stage where collection-history evidence begins; put any real percentage, receipt window, cadence, or empty-history explanation beneath it. Directory shelves may keep the stage at the bottom of the product preview because they do not expose a separate evidence column.
- Keep product stage and collection history visibly separate on product details. The collection-history section shows only observed stability/gaps or a truthful no-history state; never repeat `Observed / Planned / Pending release` inside that history visualization. Focused catalog rows may show the stage beside a concise history/evidence line so users can see why no trend exists.
- Each of the nine Data categories must own a genuinely distinct raster base grammar, not only a hue-shifted reuse of another category. Generated or supplied raster bases live under `public/assets/data-products/`; product variants may crop, rotate, mirror, offset, and echo that category base while preserving its recognisable structure.
- Data explains the user-facing A-share taxonomy, shared dataset template, receipt evidence, alternative-data families, and the proposed trial/add-on order path. Features are transparent/versioned target objects and remain labelled product-definition/planned until a real runtime plane exists. Research separates paper, industry-research, and case formats from topic taxonomy, then progressively reveals reproducible preparation methods through the question -> evidence -> limits -> Data/Feature/Method reading path.
- Data keeps connected contracts, historical collection observations, candidate sources, and the integration roadmap as four separate states on a dedicated lightweight source-landscape route. Never turn source discovery, technical reachability, registry activation, a historical success, or an unverified licence into a live, stable, redistributable, or sellable claim. Do not add a second keyword-search field there; discovery remains owned by global search.
- Dataset detail pages present their data contract and bounded `/v1/query` request example inline. Do not send users to Docs merely to see those two product-specific objects. The inline request is copy-only, never sends automatically, and must remind users to confirm the authoritative `dataset_id`, `schema_major`, and entitlement through authenticated catalog/account evidence.
- Pricing fixes three base-data plans: `Basic / 基础版`, `Professional / 专业版`, and `Flagship / 旗舰版`. All share the same base-data scope and history policy; request frequency alone differs at 200/600/1000 per minute, with no commercial daily quota or concurrency limit. Owner-confirmed monthly prices are 99/299/499; annual payment is twelve monthly prices at 10% off. The domestic-first display assumes CNY, pending settlement-currency confirmation before activation. Show actual annual totals of 1,069.20/3,229.20/5,389.20, and label the monthly equivalent as an equivalent, not a monthly charge. Do not imply automatic renewal. Alternative-data commerce remains a separate later surface, never preselected or included in base pricing. Present one base plan at a time with direct tier buttons, previous/next controls, and a monthly/annual switch. Do not use a three-card SaaS grid, needs quiz, workload configurator, granularity slider, upstream-provider matrix, per-dataset cart, or base-plus-add-on receipt. Documentation remains a searchable platform-wide help system inside Account; do not collapse it into an API-only landing page.
- Prices are confirmed display decisions, not live offers. Checkout, trial periods, real-time grants, renewal, payment and effective entitlement remain unavailable/unverified until their backend contracts and authenticated readback establish them. Never turn client state into access authority. Keep purchase controls disabled with an explicit unavailable state while payment is not implemented.
- Account identity is planned to support both verified phone and email, independent from API keys, within the existing Login/Account design. Do not introduce a second dashboard or fabricate sent codes/registration success before delivery and identity services exist. Linking either method requires verification, not string matching.

The object grammar is fixed: index pages use `orientation -> taxonomy -> object list -> evidence -> usage -> access`; detail pages use `identity -> maturity/availability -> trust/limitations -> schema/version -> related objects -> sample -> next action`. The local `productManifest.js` is design-contract content, never runtime authority.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.
